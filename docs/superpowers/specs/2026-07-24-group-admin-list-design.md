# 群組管理員名單設計

日期：2026-07-24  
範圍：LINE 群組內的管理員名單維護、權限驗證、初始化與持久化

## 1. 背景與目標

這個專案目前已經有可運作的 LINE 群組 bot、D1、Queue 與 OpenRouter 回覆流程。下一個需要補上的，是一個「群組級管理員名單」：

- 每個群組各自維護自己的管理員名單
- 只有群組內可以操作
- 只有已在名單內的人可以新增、移除、列出管理員
- 名單需要能從 `.env` 初始化，之後可透過 LINE 指令更新
- 名單需要持久化，不能只存在記憶體

這份設計只處理「管理員名單」本身，不包含之後的天氣設定、課表設定或其他功能的實際業務邏輯；但它會先把權限層打好，讓後續指令可以共用。

## 2. 設計原則

1. 以 D1 作為唯一持久化來源。`.env` 只負責初始種子，不作為運作中的權威資料。
2. 權限判斷在 Worker 內完成，不能依賴外部人工檢查。
3. 管理指令只允許在群組內執行，私訊一律拒絕。
4. 同一位成員以 `userId` 作為主鍵，以 `displayName` 作為可讀標籤。
5. 指令要容忍 LINE 顯示名稱變動，所以比對以 `userId` 為準，顯示以最新抓到的 `displayName` 為準。

## 3. 使用情境

### 3.1 一般使用者

一般群組成員傳送管理指令時，若不在管理員名單中，系統回覆權限不足。

### 3.2 已在名單內的管理員

已在管理員名單中的人可以：

- 新增管理員
- 移除管理員
- 列出目前管理員

### 3.3 首次初始化

初始管理員來源有兩種：

1. `.env` 提供的 bootstrap 種子名單
2. 群組第一次執行初始化流程時的有效操作人

第一版不直接依賴 LINE 的「群組建立者」欄位，因為 webhook 並不保證提供穩定可用的 creator metadata。實務上，如果要把某個人當作第一位管理員，最穩定的方式仍然是把他的 `userId` 先放進 `.env` 種子名單。

## 4. 指令規格

所有管理指令都要求在群組訊息中觸發，並且要由現有管理員執行。

### 4.1 新增管理員

支援兩種輸入方式：

- `@bot 管理員新增 @王小明`
- `@bot 管理員新增 Uxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`

解析規則：

- 若訊息中有 LINE mention，優先使用被 mention 的 `userId`
- 若沒有 mention，但後面是一段像 `userId` 的字串，則當作直接指定 `userId`
- `displayName` 優先取 LINE webhook 事件中的顯示名稱；若指令中有 mention，可補記該 member 當下的顯示名稱

### 4.2 移除管理員

支援兩種輸入方式：

- `@bot 管理員移除 @王小明`
- `@bot 管理員移除 Uxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx`

規則與新增相同，但若要移除的人不存在，回覆明確的「查無此管理員」。

### 4.3 列出管理員

指令：

- `@bot 管理員列表`

輸出：

- 目前群組管理員數量
- 每位管理員的 `displayName`
- 若系統有 `userId`，可在內部保留但不要直接完整曝光在訊息裡，避免把可識別資訊過度外流

### 4.4 未來擴充

本規格先預留指令路由，讓後續可擴充：

- `@bot 設定預設城市 台北`
- `@bot 設定通知時間 18:30`

這些未來指令也會共用同一套權限驗證。

## 5. 資料模型

### 5.1 D1 資料表

新增一張表 `group_admins`：

- `group_id TEXT NOT NULL`
- `user_id TEXT NOT NULL`
- `display_name TEXT NOT NULL`
- `source TEXT NOT NULL`
  - 允許值：`env`、`bootstrap`、`command`
- `created_at TEXT NOT NULL`
- `updated_at TEXT NOT NULL`

索引與約束：

- `PRIMARY KEY (group_id, user_id)`，避免重複加入
- `INDEX(group_id)`，方便列出同群組管理員

### 5.2 `.env` 初始化格式

使用一個 JSON 型環境變數作為 bootstrap 種子來源。設計目標是讓它能表示「多群組、多管理員」。

建議格式：

```json
{
  "group-id-1": [
    { "userId": "U123...", "displayName": "王小明" }
  ],
  "group-id-2": [
    { "userId": "U456...", "displayName": "小美" }
  ]
}
```

說明：

- key 是 `groupId`
- value 是該群組的初始管理員清單
- `displayName` 允許先手動填入；若沒有，也可以在第一次透過指令驗證時補寫

如果未來只服務單一群組，這個格式仍然可用，只是只有一個 key。

## 6. 初始化與同步規則

### 6.1 第一次讀到某群組時

當 Worker 第一次處理某個群組事件，而該群組在 D1 還沒有任何管理員資料時：

1. 讀取 `.env` 內對應 `groupId` 的 bootstrap 清單
2. 將清單寫入 `group_admins`
3. 寫入後，以 D1 作為權威資料源

### 6.2 指令更新後

之後所有新增或移除都直接改 D1，不再回寫 `.env`。  
`.env` 只作為「首次初始化」與「災難重建的種子來源」。

### 6.3 併發保護

同一個群組如果同時收到兩個管理指令，必須避免重複插入或覆蓋錯誤。處理方式以 D1 的主鍵約束為準，插入時使用冪等邏輯；若資料已存在，更新 `display_name` 和 `updated_at` 即可。

## 7. 權限與錯誤處理

### 7.1 權限判斷

每次管理指令都要檢查：

1. 事件是否來自群組
2. 是否為文字訊息
3. 是否是 bot 的管理指令
4. 發話者是否存在於該群組的 `group_admins`

若任一條件不成立，就直接拒絕，不進入後續處理。

### 7.2 常見錯誤回覆

建議回覆語氣簡潔，不要洩漏內部資料。

- 非群組訊息：`這個指令只能在群組內使用。`
- 非管理員：`你沒有權限執行這個指令。`
- 找不到指定成員：`找不到這位管理員。`
- 已存在：`這位管理員已在名單內。`
- 不存在：`這位管理員不在名單內。`
- 指令格式錯誤：`格式不正確，請用「@bot 管理員新增 @姓名」或「@bot 管理員新增 userId」。`

### 7.3 顯示名稱變動

如果同一個 `userId` 再次執行管理指令，系統應更新 `display_name` 為最新 webhook 看到的名稱。  
這樣管理清單會跟著 LINE 顯示名稱變化，不需要人工維護舊名稱。

## 8. 程式模組邊界

這個功能建議拆成幾個小模組：

- `src/admin/group-admins.ts`
  - 讀取 bootstrap 種子
  - 驗證使用者是否為管理員
  - 新增 / 移除 / 列出

- `src/admin/commands.ts`
  - 解析 `管理員新增 / 移除 / 列出`
  - 把 mention 和 userId 統一成結構化輸入

- `src/admin/routing.ts`
  - 決定哪個訊息是管理指令
  - 決定要交給哪個 handler

- `migrations/0002_group_admins.sql`
  - 建立 `group_admins`

這樣做的目的是把「權限」、「解析」、「資料存取」分開，避免後續天氣或其他管理指令把主流程弄得太大。

## 9. 測試範圍

### 9.1 單元測試

要覆蓋：

- `.env` bootstrap JSON 解析
- 管理員新增 / 移除 / 列表的基本行為
- mention 與 userId 兩種輸入解析
- 權限判斷：群組內 / 群組外 / 非管理員 / 已是管理員
- 重複新增、重複刪除

### 9.2 整合測試

要覆蓋：

- 群組事件進來後能正確初始化 bootstrap 名單
- 管理員指令只在群組內接受
- 未授權者無法修改名單
- 授權者可以新增後再立即列出，結果一致

### 9.3 端到端測試

至少要驗證：

- 一個 bootstrap 管理員可以在群組中新增另一位管理員
- 新增後，新的管理員可以執行列出
- 非管理員收到權限拒絕

## 10. 成功標準

這個功能算完成，需同時滿足：

- 每個群組都有獨立的管理員名單
- 名單能從 `.env` 初始化
- 名單能透過 LINE 指令新增、移除、列出
- 只有群組內且已在名單中的人能操作
- 名單資料會持久保存到 D1
- 使用者名稱變動後，系統會保留最新 `displayName`

## 11. 不在本規格內

- 群組活動建立
- 天氣查詢
- 課表排程
- 訓練提醒
- 賽事搜尋
- 管理網頁
- 多租戶後台

這些可以在後續規格中繼續加，但不應混進這一版，避免權限與業務邏輯耦合。
